# Release-readiness checklist

This checklist is intentionally stricter than “the tests pass.” Run every item against the exact
source revision and environment intended for release.

## Required automated checks

- [ ] `ruff check .`
- [ ] `ruff format --check .`
- [ ] `pytest -ra` on Python 3.11, 3.12, and 3.13 (CI matrix)
- [ ] `ResourceWarning` remains an error; no new warnings are silenced to obtain a green suite
- [ ] `python -m compileall -q nova benchmark scripts tests`
- [ ] Build wheel and source distribution with `python -m build`
- [ ] Validate package contents with `python scripts/check_wheel.py dist/*.whl`
- [ ] Install the wheel into a clean environment; run `pip check` and import the API without dev
      dependencies
- [ ] Verify CI hygiene reports no tracked caches, databases, generated bytecode, local environment
      files, or build products
- [ ] Run benchmark smoke test and inspect generated results; do not infer production quality from
      a smoke test alone

## Frontend Phase 5 checks

- [ ] `frontend/package-lock.json` is committed and `npm ci` succeeds without modifying the lockfile
- [ ] `npm run typecheck`, `npm run lint`, `npm test`, and `npm run build` pass in `frontend/`
- [ ] `npm run test:e2e` passes, including the local FastAPI contract smoke test and mobile navigation check
- [ ] Review desktop and mobile layouts; verify keyboard focus, screen-reader announcements, reduced motion, and verdict labels with text as well as color
- [ ] Built assets and source maps contain no API keys or credentials; frontend code does not write user content or secrets to local/session storage
- [ ] Hosted deployment uses a trusted same-origin BFF with real session auth, CSRF protections, and server-side tenant credential mapping; the loopback-only Vite proxy is not exposed publicly
- [ ] UI features map to real API capabilities; no fabricated memory list, activity, analytics, or provider identity is shown

## Security and deployment checks

- [ ] Production startup fails when authentication or the encryption key is missing/invalid
- [ ] Production API keys meet the minimum entropy/length policy and secrets live outside source
      control
- [ ] A shared API key cannot select a non-default tenant; tenant-specific keys cannot be overridden
      by `X-Tenant-ID`
- [ ] Tenant-scoped read, write, export, delete, audit, and storage operations are exercised with two
      distinct tenants
- [ ] SSRF tests cover literals, mixed public/private DNS answers, one-time resolution, pinned
      connections, TLS hostname verification, proxy environment variables, and redirects
- [ ] Provider/remote database credentials and full connection strings never appear in responses or
      routine logs
- [ ] PostgreSQL tests run against a real supported PostgreSQL server before claiming production
      compatibility; fake-driver tests are not a substitute
- [ ] Schema migration, backup, restore, encryption-key rotation, timeout behavior, and recovery from
      unavailable remote stores are exercised
- [ ] Retention deletion is verified for shared SQLite and configured tenant-owned databases
- [ ] Observability, rate limits, TLS termination, network egress policy, backup monitoring, and
      incident/recovery procedures are reviewed for the deployment environment

## Architecture caveats

- SQLite is the default shared local store. Each tenant with a PostgreSQL configuration is routed to
  its own database. Configuring PostgreSQL does not auto-create the database or credentials.
- `NOVA_ALLOW_PRIVATE_ENDPOINTS` is an explicit weakening of endpoint restrictions and should not
  be enabled casually.
- The HTTP provider's IP-pinning transport relies on a deliberately constrained `httpcore` 1.0.x
  interface. Keep the `<1.1` dependency bound until this is replaced with a supported public API or
  verified against a newer implementation.
- A green test suite is evidence of tested behaviors only. It does not prove the absence of security
  defects or replace deployment-specific review and staged rollout.
